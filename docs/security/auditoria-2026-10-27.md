# Auditoría defensiva de seguridad SportMaps — 2026-10-27

## Alcance y método

Revisión estática de migraciones versionadas, BFF, frontend y documentación del repositorio. No se consultó Supabase, Render, Vercel ni proveedores; no se ejecutaron migraciones ni pruebas. La auditoría no puede certificar la configuración desplegada ni el estado efectivo del catálogo de políticas. Las tablas y procedimientos citados son evidencia del código versionado, no prueba de que el mismo artefacto esté aplicado en cada ambiente.

## 1. Resumen ejecutivo

1. Las correcciones conocidas de identidad de entrenador, bucket de documentos, monto de pagos y abuso de OCR aparecen versionadas en migraciones posteriores.
2. Hay riesgo alto de exposición entre escuelas en lectura de documentos: una policy versionada permite a staff de cualquier escuela leer documentos de identidad de cualquier tenant.
3. El plan de ambientes reconoce que dev/stg/prod comparten la misma instancia Supabase; el aislamiento real sigue pendiente y debe tratarse como prioridad operativa.
4. Existe una Edge Function Wompi heredada con lógica incompleta de conciliación; su despliegue actual es desconocido y requiere confirmar/desactivar si aún está publicado.
5. El BFF usa `service_role`, por lo que cada ruta debe aplicar autorización y scoping propios; la documentación de arquitectura no sustituye verificación completa endpoint por endpoint.
6. No hay base para afirmar que la clave service role está actualmente expuesta en el frontend o en archivos versionados. Los archivos `.env` locales no aparecen en el inventario de Git consultado.
7. No se consultaron CVEs ni se ejecutó `npm audit`; el reporte de dependencias del plan del 21-oct no es verificación del estado actual.
8. IA por WhatsApp, marketplace clínico y expansión de pagos deben bloquearse hasta cerrar el tenant boundary y la revisión de autorización/auditoría.

- Meta/WhatsApp: el BFF configura raw body y tiene verificación HMAC del webhook (`bff/src/index.ts:278-282`; `bff/src/routes/whatsapp.ts:124-127`; `bff/src/services/whatsapp.service.ts:92-110`). No se encontró evidencia de omisión general de firma en ese handler.
- Wompi BFF: el handler actual declara verificación de checksum multi-tenant, reconsulta de transacción e idempotencia (`bff/src/routes/wompi.ts:24-30`, `:222-296`). Esto reduce el riesgo de SEC-03 si es el endpoint realmente configurado.
- OCR WhatsApp: el límite por número y escuela está implementado en `20261025205950_wa_limite_comprobantes_ocr.sql` y la RPC recibe el id de cola para obtener tenant/número desde BD (comentarios y cuerpo, líneas 25-30 y 103-120).
- CSP/CORS/rate limiting: existen configuraciones en `bff/src/index.ts:147-204` y `:242-282`; la existencia no sustituye validar allowlists y límites por endpoint público.

## 6. Discrepancias entre specs y código

- `docs/architecture/security.md` describe un flujo genérico donde `x-school-id` viaja desde frontend y `requireAuth` valida membresía (`docs/architecture/security.md`, sección “Multitenancy”). La separación de ambientes reconoce a la vez que los servicios comparten proyecto Supabase (`docs/specs/separar-prod-de-dev-stg.md:11-23`). En la práctica, el aislamiento debe venir de membresía/ownership en el BFF y policies, no solo del header.
- `docs/specs/sportmaps-agents-platform.md:1-18` presenta Pay/Connect/Analytics como agentes existentes y Connect como síncrono; el spec profesional actualizado especifica consentimiento clínico y canal existente con firma/opt-in (`docs/specs/profesionales-independientes-agentes-ia.md:10-16`). El contrato genérico de agentes no define autorización tool-level ni frontera de datos; el spec profesional sí cierra algunos controles, pero falta completar consentimiento legal del menor.
- `docs/specs/separar-prod-de-dev-stg.md` es un plan, no evidencia de separación ya realizada. Tratar la separación como pendiente hasta revisar configuración en los tres deploys.
- El plan de débito automático mantiene preguntas/grants a validar (`docs/plan-debito-automatico.md:37-46`, `:57-81`), mientras la hoja de ruta de seguridad del 21-oct las describe como tareas. Ningún documento equivale a evidencia de grants efectivos ni de seguridad de tokens desplegados.
- El repo contiene tanto `supabase/functions/wompi-webhook/index.ts` como el webhook BFF `bff/src/routes/wompi.ts`. El BFF documenta checksum multi-tenant, reconsulta e idempotencia; la Edge Function antigua no refleja ese nivel de conciliación. Es una discrepancia de código que exige identificar cuál está publicado y configurado.
- Los documentos de seguridad registran que `identity-documents` pasó a privado; la policy concreta de staff sigue sin scoping por escuela. El bucket privado evita el acceso anónimo directo, pero no logra la regla no negociable de tenant isolation para lecturas autenticadas.

## Limitaciones explícitas

No se revisó configuración de consola ni datos vivos; no se llamó a producción ni a APIs externas. La revisión de Git fue de rutas/commits de configuración nombrados, no un escaneo exhaustivo de blobs históricos del repositorio remoto. No se ejecutó `npm audit`, pruebas dinámicas, fuzzing, análisis SAST ni simulación de pagos. Los puntos etiquetados “SOSPECHA - VERIFICAR” no son hallazgos confirmados.
